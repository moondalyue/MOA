# 이메일·비밀번호 회원가입 방식 선택

이 문서는 비개발자가 이메일·비밀번호로 가입하는 서비스를 만들 때 인증 방식을 선택하기 위한 안내입니다. 모든 방식을 설치하는 절차가 아닙니다. 한 가지 방식을 선택하고 구현 계획을 확인한 뒤 필요한 패키지만 추가하세요.

기본 실행은 [설치 안내](SETUP.md), DB 연결은 [Supabase 설정](SUPABASE_SETUP.md), 실제 배포는 [Vercel 배포 안내](VERCEL_DEPLOYMENT.md)를 참고하세요.

## 현재 보일러플레이트 상태

- 이 프로젝트는 Supabase Auth를 선택하여 `@supabase/supabase-js`와 `@supabase/ssr`를 사용합니다. 아래 다른 방식 비교는 선택 참고 자료이며 동시에 설치할 필요가 없습니다.
- `User.authUserId`로 인증 사용자와 앱 회원을 연결하고 `Activity.userId`로 활동 소유자를 관리합니다. 기존 회원 ID는 유지하며 이메일 일치만으로 기존 계정을 자동 연결하지 않습니다.
- 가입·로그인·로그아웃·비밀번호 재설정, PKCE 인증 콜백, 쿠키 세션 갱신과 회원별 활동 CRUD 코드가 있습니다. 실제 환경 설정·DB 적용·이메일 수신 검증은 별도입니다.
- 비밀번호와 세션은 Supabase Auth가 관리하며 앱 회원 테이블에는 저장하지 않습니다. DB 연결 검사 성공은 인증·권한 검증 완료가 아닙니다.

## 현재 프로젝트의 Supabase Auth 연결

1. 사용할 Supabase 프로젝트와 개발·운영 환경을 확인합니다. `.env.example`을 참고하여 `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`, 서버 기준 주소 `APP_URL`을 실제 환경에 준비합니다. DB용 `DATABASE_URL`·`DIRECT_URL`은 기존 설정을 유지합니다. 실제 비밀값은 Git·채팅·로그에 올리지 않습니다.
2. 사용자가 선택한 방식은 **이메일 인증 없이 가입 직후 로그인**입니다. Supabase 대시보드의 이메일 공급자 설정에서 Confirm Email을 꺼야 가입 응답에 세션이 반환됩니다. 앱 코드는 이 설정을 변경하지 않습니다. 이메일 소유를 확인하지 않으므로 타인의 이메일 입력·주소 오입력 가능성이 있으며 이메일만으로 기존 회원 연결이나 추가 권한을 부여하지 않습니다. 일반 사용자 공개 전 소유 확인과 계정 복구 방침을 재검토합니다. 새 비밀번호는 12자 이상, UTF-8 기준 72바이트 이내이며 공급자의 더 강한 규칙도 충족해야 합니다. 닉네임은 1~50자이며 중복을 허용합니다.
3. Auth URL 설정에서 Site URL을 `APP_URL`과 맞추고, Redirect URLs에 `${APP_URL}/auth/callback` 및 `${APP_URL}/auth/callback?next=/auth/update-password`를 등록합니다. 실제 설정에는 `${APP_URL}`을 로컬 또는 배포 주소로 바꿔 입력합니다. 운영 주소에는 HTTPS를 사용하며 불필요하게 넓은 와일드카드는 허용하지 않습니다.
4. 기본 PKCE 흐름의 메일 링크가 Supabase 인증을 거쳐 앱의 `/auth/callback`으로 `code`를 전달하도록 합니다. 기존 메일 템플릿을 수정했다면 `ConfirmationURL`과 redirect 전달을 검토합니다. 인증을 시작한 동일 브라우저의 PKCE 쿠키가 필요하며 링크 만료·재사용 시 다시 요청합니다.
5. 비밀번호 재설정 메일을 보낼 SMTP·수신 대상·발송 제한을 준비합니다. 가입 메일 인증 생략과 계정 복구 메일 제공은 별개입니다. 앱 코드 구현만으로 메일 도착이 보장되지 않습니다. 공개 서비스는 실제 수신·만료·재사용과 발송 제한을 검증해야 합니다.
6. 실제 DB 적용 전에 기존 회원·활동 데이터의 보존 필요성과 대상 환경을 확인하고 마이그레이션 SQL·DB 역할·Data API 노출·RLS를 검토합니다. 스키마 수정만으로 실제 테이블·RLS·auth 스키마 외래 키가 생성되지는 않습니다. Supabase 관리 대상인 `auth` 스키마를 Prisma로 임의 관리하지 않습니다.
7. 기존 `users.email`과 새 인증 사용자의 이메일이 겹쳐도 자동으로 연결하지 않습니다. 기존 계정 연결은 소유권을 확인한 별도 이관 절차로 수행합니다. 정상 연결된 회원의 이메일 사본은 로그인·콜백 시 검증된 Auth 이메일로 동기화하며 충돌하면 기존 데이터를 덮어쓰지 않습니다.

화면 경로는 `/auth/signup`, `/auth/login`, `/auth/forgot-password`, `/auth/update-password`입니다. 첫 접속(`/`) 시 비회원은 로그인 화면으로, 회원은 `/dashboard`로 이동합니다. 가입·로그인 또는 일반 인증 콜백 성공 시 앱 회원 연결을 완료하고 `/dashboard`로 이동합니다. 이미 앱 회원 연결이 완료된 사용자가 로그인·가입 화면에 다시 접근해도 대시보드로 이동합니다. 연결이 누락된 사용자는 로그인 화면에 머물러 재연결할 수 있으며 반복 실패는 DB 적용·이메일 충돌·환경 설정을 확인해야 합니다. 비밀번호 재설정 콜백은 `/auth/update-password`로 이동합니다.

대시보드에는 로그인 회원의 전체 기간·유형별 활동 수, 누적 봉사 시간과 FullCalendar 활동 달력을 표시합니다. 한국 시간의 현재 월에서 시작하며 활동 시작일에 학교·교외·봉사 아이콘을 표시합니다. 날짜·아이콘 선택 시 해당 날짜의 활동과 수정 링크를 제공합니다. 연월 이동·오늘 이동·날짜 입력과 같은 날짜의 여러 활동 보기를 지원합니다.

달력은 연도 단위로 본인 자료를 조회하고 화면별 메모리에서 재사용합니다. 12월에는 다음 연도, 1월에는 이전 연도를 미리 조회하며 표시 월은 자동으로 넘기지 않습니다. 서버는 매 요청마다 로그인 회원을 다시 확인하고 소유자·연도 조건을 적용합니다. 캐시는 다른 회원이나 화면과 공유하지 않으며 로그인 만료를 확인하면 초기화합니다. 활동 저장·삭제 후 대시보드도 갱신합니다. 활동 등록과 전체 목록은 `/portfolio/new`, `/portfolio`로 연결합니다.

달력은 `@fullcalendar/react` 7.1.3과 필수 Temporal 의존성을 사용합니다. 날짜 격자·상호작용·한국어·Monarch 테마는 같은 패키지에서 제공되며 유료 기능은 사용하지 않습니다. MIT 라이선스 고지는 설치 패키지의 LICENSE.md에 있습니다. [FullCalendar React 안내](https://fullcalendar.io/docs/react)

포트폴리오는 회원 전용입니다. 목록·수정 화면·저장·삭제 서버 처리에서 검증된 사용자와 소유권을 확인합니다. 공개 여부는 저장하지만 공개 공유 화면은 제공하지 않으며 현재 활동 목록은 본인만 볼 수 있습니다. 첨부 파일 기능과 계정 탈퇴·연쇄 삭제는 포함하지 않습니다. 로그아웃은 현재 브라우저 세션을 종료하며 탈취된 접근 토큰의 즉시 무효화까지 보장하는 기능으로 해석하지 않습니다.

`User.authUserId`는 기존 데이터 보존을 위해 선택값으로 시작하며, 연결되지 않은 회원에게 활동 권한을 주지 않습니다. 현재 필드에는 앱 차원의 연결만 있고 `auth.users`로 향하는 DB 외래 키는 없으므로 실제 DB 적용 시 연결 무결성·계정 삭제 정책을 별도 검토합니다. Prisma 연결에는 Auth 세션이 자동 전달되지 않습니다. 서버 권한 검사와 Data API/RLS 검토가 모두 필요합니다.

자동 검사는 `npm run db:validate`, `npm run check`, `npm run build`로 수행합니다. 입력·리디렉션·회원 연결·활동 권한·대시보드 집계·달력 연도 경계·캐시 검사는 `node --experimental-test-module-mocks --import tsx --test tests/auth-activity.test.ts tests/auth-session.test.ts tests/portfolio-authorization.test.ts tests/dashboard.test.ts tests/auth-redirects.test.ts tests/calendar.test.ts tests/calendar-server.test.ts`로 실행합니다. 모의 검사는 실제 Supabase 인증·RLS·DB CRUD를 검증하지 않습니다.

## 먼저 알아둘 용어

| 용어      | 쉬운 설명                                                                          |
| --------- | ---------------------------------------------------------------------------------- |
| 회원가입  | 서비스에서 사용할 계정을 만드는 과정                                               |
| 인증      | 로그인한 사람이 누구인지 확인하는 과정                                             |
| 권한 확인 | 그 사람이 어떤 자료를 조회·수정할 수 있는지 확인하는 과정                          |
| 세션      | 로그인 상태를 유지하고 확인하기 위한 정보                                          |
| JWT       | 서명 등을 검증해 사용하는 토큰 형식. 회원가입 전체를 구현해 주는 라이브러리가 아님 |

Next.js는 화면과 서버 코드를 실행하는 프레임워크입니다. 완성된 회원가입 기능이 기본으로 들어 있는 것은 아닙니다. 인증 라이브러리나 인증 서비스를 연결해야 하며, Next.js 공식 안내도 인증 라이브러리 활용을 권장합니다. [Next.js 인증 안내](https://nextjs.org/docs/app/guides/authentication)

Supabase는 DB만 사용할 수도 있습니다. 이 경우 회원가입·로그인은 Next.js 앱의 인증 라이브러리가 처리하고, 데이터를 Prisma로 Supabase PostgreSQL에 저장합니다.

패키지 설치와 지원 범위는 [Supabase Next.js 연동](https://supabase.com/docs/guides/auth/server-side/creating-a-client), [Better Auth 설치](https://better-auth.com/docs/installation), [Better Auth Prisma 연동](https://better-auth.com/docs/adapters/prisma), [Better Auth 이메일·비밀번호](https://better-auth.com/docs/authentication/email-password), [Auth.js Credentials](https://authjs.dev/getting-started/authentication/credentials), [Auth.js Prisma 연동](https://authjs.dev/getting-started/adapters/prisma)을 기준으로 확인합니다.

### 어떤 방식을 고르면 되나요?

- **Supabase Auth:** Supabase에서 DB와 인증을 함께 관리하고 싶은 경우 먼저 검토하세요.
- **Better Auth:** Supabase는 DB로만 사용하고, 앱에서 이메일·비밀번호 가입을 구성하고 싶은 경우 먼저 검토하세요.
- **Auth.js:** 기존에 사용 중이거나 요구사항에 맞는 이유가 있을 때 검토하세요. Credentials만 추가하면 가입·이메일 인증·비밀번호 재설정까지 완성되는 것으로 생각하면 안 됩니다.

이는 이 보일러플레이트의 선택 안내이며 특정 방식의 도입을 확정한 것은 아닙니다. 패키지 수가 적다는 이유만으로 설정·운영 부담도 적다고 판단하지 마세요. 실제 설치 시에는 Next.js·Prisma·Node.js 버전과 라이브러리의 안정 버전·지원 범위를 다시 확인합니다.

## 기존 패키지는 무엇을 재사용하나요?

다음 패키지는 이미 `package.json`에 포함되어 있습니다. 복사한 프로젝트에서 `npm ci`로 설치하며 인증 도입 때문에 중복 설치할 필요는 없습니다.

| 기존 패키지                  | 활용할 역할                                                       |
| ---------------------------- | ----------------------------------------------------------------- |
| `react-hook-form`            | 가입·로그인 화면의 입력 폼 관리                                   |
| `zod`, `@hookform/resolvers` | 이메일 형식·비밀번호 규칙 등 입력 검증. 서버에서도 별도 검증 필요 |
| `prisma`, `@prisma/client`   | 선택한 인증 방식의 모델 관리와 앱 데이터 조회·저장                |
| `@prisma/adapter-pg`, `pg`   | 현재 서버의 PostgreSQL 연결                                       |

폼 입력 검증만으로 로그인한 사용자가 확인되거나 데이터 접근 권한이 생기지는 않습니다.

### 추가 패키지를 읽는 방법

- Supabase의 `@supabase/supabase-js`는 인증 등 Supabase API를 호출하는 SDK이며, `@supabase/ssr`는 Next.js 같은 환경에서 쿠키 기반 세션 연동에 사용합니다. 기존 Prisma DB 연결을 대체할 필요는 없습니다.
- Better Auth는 본체 `better-auth`와 현재 공식 Prisma 안내의 `@better-auth/prisma-adapter`를 구분합니다. 과거 예제의 `better-auth/adapters/prisma` 경로와 혼합하지 말고 선택한 버전의 공식 안내를 확인하세요.
- Auth.js의 `@auth/prisma-adapter`는 DB 연동용입니다. Credentials의 회원 저장·비밀번호 관리가 어댑터 설치만으로 자동 구현되는 것은 아니며, 세션 전략에도 제약이 있는지 확인해야 합니다.
- 메일 발송이나 별도 비밀번호 해싱에 필요한 추가 패키지는 선택한 서비스·구현 방식에 따라 정합니다. 세 방식에 공통으로 특정 메일·해싱 패키지를 미리 설치하지 않습니다.

이 문서에는 일괄 설치 명령을 제공하지 않습니다. 선택과 호환성 확인 전 모든 인증 패키지를 설치하거나, 기존 Prisma 설정을 다시 초기화하지 마세요.

## 선택 후 달라지는 부분

### Supabase Auth를 선택하면

인증 계정은 Supabase의 `auth.users`에서 관리합니다. 앱 회원 정보는 인증 사용자의 고유 ID와 연결하도록 설계합니다. 현재 `User.id`의 독립 UUID 생성 방식을 그대로 두고 연결이 끝났다고 판단하지 않습니다. 이메일 주소만으로 계정을 자동 연결하지 마세요. [Supabase 회원 데이터 관리](https://supabase.com/docs/guides/auth/managing-user-data)

프로젝트 URL·공개용 키, 이메일 인증 포함 여부, 허용 리디렉션 주소, 쿠키와 세션 갱신을 설정해야 합니다. 로컬 주소와 실제 배포 주소는 각각 확인합니다. 공개용 키와 서버 전용 비밀키를 구분하고, 비밀키를 브라우저에 전달하지 않습니다.

### Next.js 인증 라이브러리를 선택하면

Supabase Auth를 사용하지 않아도 됩니다. 회원·계정·세션 등은 선택한 라이브러리에 맞춰 앱 DB에 구성합니다. 기존 `User`와 라이브러리가 요구하는 필드·ID 타입·모델 이름을 비교한 뒤 변경안을 정합니다. 라이브러리 예제 스키마를 기존 파일 전체에 덮어쓰지 않습니다.

기존 `DATABASE_URL`, `DIRECT_URL`, `certs/supabase-ca.crt` 연결 구성을 유지하면서 연동을 검토합니다. 인증용 비밀값·앱 기준 URL·이메일 발송 설정은 선택한 방식에 따라 추가하며, 실제 비밀값은 Git에 올리지 않습니다.

### JWT를 따로 선택해야 하나요?

먼저 인증 서비스·라이브러리를 선택한 뒤, 요구사항에 맞는 세션 방식을 정합니다. JWT와 DB 세션은 로그인 상태를 다루는 방식이며 회원가입 서비스 자체가 아닙니다. 라이브러리별 지원 범위가 다르므로 원하는 조합이 가능한지 확인해야 합니다.

JWT만으로 회원가입을 직접 구현하려면 비밀번호 해싱, 토큰 만료·갱신·폐기, 쿠키 보안 등까지 설계해야 합니다. 이 보일러플레이트에서는 인증 서비스나 라이브러리가 제공하는 기능을 우선 검토합니다.

## 메일 인증에 필요한 준비

여기서 메일 인증은 가입자가 해당 이메일 주소를 실제 사용할 수 있는지 확인하는 절차입니다. 이메일 형식 검사나 비밀번호 로그인과는 다르며, 사람의 실명·신원까지 확인하는 것은 아닙니다.

| 항목        | 준비·확인할 내용                                                             |
| ----------- | ---------------------------------------------------------------------------- |
| 이메일 발송 | SMTP 또는 이메일 발송 서비스, 서버 전용 발송 인증 정보                       |
| 발신자 설정 | 발신 주소, 서비스가 요구하는 발신 도메인과 DNS 인증                          |
| 인증 처리   | 선택한 인증 도구의 링크·토큰 발급, 만료·재사용 방지, 재발송 제한             |
| 화면        | 메일 확인 안내, 인증 완료·만료·발송 실패·재발송 안내                         |
| 환경별 주소 | 로컬·Preview·Production의 기준 URL, 허용 리디렉션과 인증 완료 경로           |
| 검증        | 실제 수신·스팸함, 올바른 계정의 인증 처리, 잘못되거나 만료된 링크, 발송 제한 |

Supabase의 기본 발송 서비스는 수신 대상 등에 제한이 있으므로, 일반 사용자에게 메일을 보내려면 별도 SMTP 설정을 검토해야 합니다. 발송 제한과 제공 조건은 실제 도입 시 공식 안내에서 확인하세요. [Supabase SMTP 안내](https://supabase.com/docs/guides/auth/auth-smtp)

Better Auth는 이메일 인증·비밀번호 재설정 기능과 발송 콜백을 연결해야 합니다. Auth.js의 Credentials를 사용할 때는 해당 기능을 별도로 구성해야 합니다. 인증 도구가 제공하는 토큰 검증을 우선 활용하며 발송 패키지 설치만으로 인증 처리가 끝났다고 판단하지 않습니다. [Better Auth 이메일 안내](https://better-auth.com/docs/concepts/email), [Auth.js Credentials](https://authjs.dev/getting-started/authentication/credentials)

## MVP에서는 메일 인증을 생략해도 되나요?

MVP라는 이름만으로 일괄 제외하지 않고 사용자 범위와 이메일 소유 확인이 필요한 기능을 먼저 검토합니다. 현재 프로젝트는 사용자가 가입 메일 인증 생략을 선택했으며, 위의 현재 프로젝트 연결 절차를 따릅니다. Supabase 대시보드 설정은 앱 코드와 별도로 확인해야 합니다.

| 사용 범위                | 제안할 방향                                                  | 확인할 제한                                                        |
| ------------------------ | ------------------------------------------------------------ | ------------------------------------------------------------------ |
| 내부 시연·제한된 테스트  | 메일 인증을 생략하고 가입·로그인 흐름부터 검증하는 선택 가능 | 실제 이메일 소유가 확인되지 않음. 제한된 테스트 계정과 데이터 사용 |
| 일반 사용자에게 공개     | 메일 인증 포함을 우선 검토                                   | 주소 오입력·타인 주소 가입·계정 복구·초대 등 관련 기능 영향        |
| 이후 메일 인증 추가 예정 | 생략한 범위와 도입 조건을 계획에 기록                        | 기존 미검증 회원의 재인증·접근 제한·안내 방침 필요                 |

생략 여부는 영향을 설명한 뒤 사용자가 결정합니다. 미검증 주소를 신뢰해 다른 계정과 자동 연결하거나 조직·역할·접근 권한을 부여하지 않습니다. 메일 인증을 생략해도 비밀번호 해싱, 서버 입력 검증, 세션과 데이터 접근 권한 확인은 유지합니다.

### 인증 방식별로 확인할 점

- **Supabase Auth:** `Confirm Email`을 끄면 실제 메일 확인 없이 주소가 인증된 것으로 처리됩니다. 이때 DB의 인증 표시를 실제 소유 확인의 증거로 사용하면 안 됩니다. 이후 다시 켜더라도 기존 회원의 실제 소유 확인이 소급해 완료되는 것은 아니므로 별도 재인증 방침을 검토합니다. [Supabase 일반 설정](https://supabase.com/docs/guides/auth/general-configuration)
- **Better Auth:** 이메일·비밀번호 로그인에 인증을 필수로 할지와 인증 메일을 발송할지를 구분해 설정합니다. 인증 없이 로그인한다고 해서 `emailVerified`를 임의로 참으로 바꾸지 않습니다. 실제 옵션과 동작은 선택한 버전에서 확인합니다. [Better Auth 이메일·비밀번호](https://better-auth.com/docs/authentication/email-password)
- **Auth.js:** 가입 처리와 이메일 검증 상태·로그인 허용 정책을 별도로 설계합니다. Credentials나 DB 어댑터 설치만으로 이 정책이 생기는 것은 아닙니다.

### 비밀번호 재설정은 별도 선택입니다

가입 메일 인증을 생략해도 이메일로 비밀번호를 재설정하려면 발송 설정과 안전한 재설정 링크 처리가 필요합니다. 이메일 발송까지 미룬 제한된 테스트라면 비밀번호 재설정도 미구현임을 명시하고, 테스트 계정의 복구·재발급 절차와 담당자를 정합니다. 실제 사용자에게 공개하기 전에는 복구 방침을 다시 검토하세요. 이메일 주소만 제시했다고 비밀번호를 바꾸거나 계정 접근을 허용하지 않습니다.

### 에이전트가 제안할 순서

사용 범위 확인 → 메일 발송 준비 확인 → 인증 포함·생략의 영향과 계정 복구 설명 → 사용자 선택 → 승인 범위에서 구현·검증 순으로 진행합니다. 계획에는 메일 인증 포함 여부, 비밀번호 재설정 제공 여부, 생략 이유·제한·추후 도입 조건을 구분해 남깁니다. 설정 변경이나 기존 회원의 인증 상태 변경은 문서 안내만으로 실행하지 않습니다.

## 두 방식 모두 필요한 확인

- 가입, 로그인·로그아웃, 로그인 유지·만료의 흐름을 정하고, 메일 인증과 비밀번호 재설정의 포함·생략 여부를 각각 선택합니다.
- 비밀번호 원문을 DB·로그·계획 파일에 저장하지 않습니다. 인증 담당 서비스·라이브러리의 안전한 처리 방식을 따릅니다.
- 이메일을 사용하는 기능은 발송 서비스·발신 도메인·발송 제한을 확인하고 실제 메일 도착과 링크 동작을 검증합니다. 생략했다면 미구현 범위와 제한을 남깁니다.
- 서버에서 인증 사용자와 데이터 소유권·역할을 확인합니다. 화면에서 버튼을 숨기거나 페이지 이동을 막는 것만으로 권한 처리가 끝나지 않습니다.
- Supabase Auth 세션은 Prisma 연결에 자동 전달되지 않습니다. 연결 역할에 따라 RLS를 우회할 수 있으므로 서버의 권한 검사가 필요합니다. 브라우저에서 Data API를 사용한다면 해당 테이블의 RLS 정책도 별도로 설계합니다.
- 사용자별 세션·개인정보를 공용 캐시에 넣지 않습니다. 현재 Cache Components 설정을 고려해 쿠키·인증 처리를 구현합니다.
- 잘못된 비밀번호, 중복 가입, 과도한 요청, 다른 회원 데이터 접근을 검증합니다. 메일 인증·재설정을 포함했다면 미인증 이메일과 만료·재사용된 링크도 확인하고, 생략했다면 선택한 로그인·복구 정책과 일치하는지 검증합니다.

## 선택 후 에이전트에 요청하기

아래에서 `[선택한 방식]`을 Supabase Auth, Better Auth 또는 Auth.js로 바꿔 요청할 수 있습니다.

```text
docs/AUTHENTICATION.md를 기준으로 [선택한 방식]을 사용한
이메일·비밀번호 회원가입을 계획해 주세요.

사용 범위는 [내부 시연·제한된 테스트 / 일반 사용자 공개]입니다.
가입, 로그인·로그아웃, 회원 전용 접근을 검토하고,
메일 발송 준비 사항과 메일 인증 포함·생략의 영향을 비교해 주세요.
비밀번호 재설정은 별도로 검토하고, 생략 시 계정 복구 제한과
추후 도입 조건을 설명한 뒤 선택을 확인해 주세요.
현재 User 모델과 선택한 라이브러리의 버전 호환성을 확인하고,
필요한 패키지·환경 변수·DB 변경·화면·권한 검증을 제시해 주세요.
계획 파일이 필요한 이유와 작성 여부도 먼저 확인해 주세요.
아직 파일 수정, 패키지 설치, 마이그레이션이나 배포는 진행하지 마세요.
```

진행 순서는 **요구사항 분석·계획 → DB 분석·필요 시 수정 → 서버 처리 → 화면 구현 → 연결·권한·동작 검증**입니다. [Codex 사용 안내](CODEX_GUIDE.md)와 [계획 작성 안내](../plans/README.md)를 함께 참고하세요.

인증 방식 선택이나 계획 작성 승인을 패키지 설치·구현·실제 DB 변경·배포 승인으로 확대하지 않습니다. 승인받은 범위에서 진행하고, 로컬 인증 검증과 Vercel 배포 후 검증 결과는 구분해 기록합니다. 이 문서 추가만으로 인증 기능이 구현되거나 검증된 것은 아닙니다.
